# 第4章 変更を支える設計 改訂設計メモ

## 章の狙い

動くプログラムを、変更し続けられるソフトウェアへ育てるための設計原則を扱います。ソフトウェア危機から、分割統治、情報隠蔽、抽象化、UML、OOP、関数型、テスト、品質維持へ進めます。

## 本文で必ず書くこと

- ソフトウェア危機は歴史紹介にとどめず、規模・相互作用・変更コストの問題として現在の開発に接続します。
- 凝集度・結合度・情報隠蔽を、注文確認AIの変更要求に耐える境界設計として説明します。
- UMLは図を描くこと自体ではなく、静的構造と動的振る舞いを共有するための最低限の言語として扱います。
- OOPと関数型は優劣ではなく、変更点・状態・副作用の置き方の違いとして説明します。
- テスト・レビュー・リファクタリング・技術的負債を、品質を維持する日常の活動としてまとめます。

\chapter{プログラムが動く場所}
\label{chap:runtime-data}

\begin{chapterabstract}
命令へ変換されたコードは、まだ保存装置上のファイルにすぎません。送信ボタンに反応するには、OSからCPU時間とメモリを受け取り、動いているプロセスにならなければなりません。ここで、プログラムは初めて現実の場所と時間を持ちます。

入力された文は文字列としてメモリへ置かれ、注文番号や会話履歴は型のある値へ組み直されます。その値を配列、スライス、マップのどれで持つかによって、探し方、共有のされ方、必要な時間と容量が変わります。この章では、OSが用意する舞台からデータ一つひとつの寿命まで、実行中の要求が占める場所を追います。
\end{chapterabstract}


\section{OSの役割}
\label{sec:03-runtime-data-01}

機械語になったAIアプリを起動するとき、CPUや物理メモリを直接占有することはできません。同じ端末ではブラウザ、エディタ、別のサービスも動いています。それらの間に立ち、安全に資源を分けながら共通の操作を提供するのがOSです。

\begingroup
  \centering
  \begin{tikzpicture}[node distance=3mm,every node/.append style={font=\small}]
    \node[box,minimum width=29mm] (app1) {アプリA};
    \node[box,minimum width=29mm,right=of app1] (app2) {アプリB};
    \node[accentbox,minimum width=68mm,below=of $(app1)!0.5!(app2)$] (os) {OS：抽象化・保護・資源管理};
    \node[box,minimum width=68mm,below=of os] (hw) {CPU・メモリ・ストレージ・入出力装置};
    \draw[flow] (app1) -- (os);
    \draw[flow] (app2) -- (os);
    \draw[flow] (os) -- (hw);
  \end{tikzpicture}
  \vspace{4mm}
\begingroup
\paragraph{抽象化}
        ファイル、プロセス、仮想メモリなど、ハードウェアより扱いやすい単位を提供します。

\par
\endgroup
\medskip
\begingroup
\paragraph{保護}
        権限とアドレス空間を分け、ある処理の誤りが別の処理へ波及する範囲を抑えます。

\par
\endgroup
\medskip
\begingroup
\paragraph{資源管理}
        CPU時間、物理メモリ、入出力装置を複数の処理へ割り当てます。

\par
\endgroup
  \source{Arpaci-Dusseau et al., \textit{Operating Systems: Three Easy Pieces}}
\par
\endgroup


\section{プログラムとプロセス}
\label{sec:03-runtime-data-02}

保存されている命令列はプログラムであり、まだ時間の中を進んでいません。OSが命令とデータをメモリへ配置し、実行位置や資源を管理し始めると、プログラムはプロセスになります。送信イベントを受け取るのはファイルではなく、この動いている存在です。

\begingroup
\begingroup
\paragraph{プログラム}
        命令や初期データを含む静的な記述です。実行可能ファイルやスクリプトは、それだけではCPU時間を持ちません。

\paragraph{プロセス}
        実行中のプログラムに、アドレス空間、レジスタ状態、開いているファイルなどの実行文脈を加えたものです。

\par
\endgroup
\medskip
\begingroup
\paragraph{スレッド}
        プロセス内の実行の流れです。同じプロセスのスレッドはアドレス空間などを共有し、各スレッドはレジスタ状態とスタックを持ちます。

\paragraph{並行性の注意}
        共有データへの読み書きが競合すると、実行順によって結果が変わります。同期で許される順序を定めます。

\par
\endgroup
  \takeaway{同じプログラムを2回起動すると、通常は別のプロセスと別の仮想アドレス空間が作られます。}
\par
\endgroup


\section{システムコール}
\label{sec:03-runtime-data-03}

プロセスは自由に機器を操作できるわけではありません。入力を受け取り、ファイルを読み、ネットワークへ書くときは、保護された境界を越えてOSへ依頼します。アプリの関数呼び出しが機械全体の操作へつながる狭い入口がシステムコールです。

      \end{tikzpicture}
\par
\endgroup
\medskip
\begingroup
\paragraph{代表例}
        ファイルの読み書き、ネットワーク通信、仮想メモリの操作、プロセス生成などを依頼します。

\paragraph{ライブラリとの違い}
        通常の関数呼び出しだけで完結する処理もあります。API呼び出しが必ず1対1のシステムコールになるとは限りません。

\par
\endgroup

\endgroup


\section{仮想メモリ}
\label{sec:03-runtime-data-04}

送信された文を処理するには置き場所が要りますが、すべてのプロセスへ物理メモリの番地を直接見せると、互いのデータを壊しかねません。OSとCPUは、各プロセスに自分だけの連続した空間があるように見せ、必要な物理領域へ対応づけます。

\endgroup
\medskip
\begingroup
\paragraph{プロセスごとの見え方}
        同じ数値の仮想アドレスでも、プロセスごとに異なる物理ページへ対応できます。

\paragraph{得られる性質}
        分離、疎なアドレス空間、共有ページ、必要時の割り当てなどを実現できます。

\par
\endgroup

\endgroup


\section{アドレス空間}
\label{sec:03-runtime-data-05}

仮想メモリによって得た空間の中でも、値の役割と寿命は同じではありません。命令、固定データ、関数呼び出しの途中状態、実行中に増減するオブジェクトを分けて置くことで、プロセスは大きな処理を整理します。

\endgroup

\paragraph{ヒープ}
        呼び出しの終了を越えて生きる値など、動的な寿命の記憶領域に使います。確保と再利用はランタイムやアロケータが管理します。

\section{ポインタと参照}
\label{sec:03-runtime-data-06}

値を別の関数へ渡すたびにすべて複製すると、大きな会話履歴や注文情報の扱いは重くなります。そこで、値そのものではなく置き場所を示し、同じ領域を複数の箇所から参照します。効率を得る代わりに、誰と状態を共有しているかを意識する必要が生まれます。

\begingroup
\begingroup
\paragraph{ポインタ／参照}
        別の値へ到達するための情報です。複数の変数が同じ対象を共有すると、一方の更新を他方から観測できます。

\par
\endgroup
\medskip
\begingroup
\paragraph{寿命の誤り}
        解放済み領域を指す参照や、必要な値を早く解放する処理は不正アクセスにつながります。

\par
\endgroup
\medskip
\begingroup
\paragraph{GC}
        ガベージコレクションは到達可能性などを基準に、不要になった領域を自動で再利用します。資源解放の時刻までは保証しません。

\par
\endgroup
  \vspace{4mm}
\paragraph{Goでの境界}
    Goはポインタを持ちますが、通常のポインタ演算は認めません。値をスタックかヒープのどちらへ置くかは、エスケープ解析などを用いる処理系の判断です。

  \source{The Go Programming Language Specification; Go FAQ, “stack or heap”}
\par
\endgroup


\section{型}
\label{sec:03-runtime-data-07}

メモリ上では、注文番号も文字列もポインタもビットの並びです。プログラムがそれらを取り違えずに操作できるのは、値の集合と許される操作を型として定めるからです。第1章で外側にあった解釈規則が、ここでは言語の約束として現れます。

\begingroup
\begingroup
\paragraph{型が表すもの}
        値の集合、利用できる演算、式の組み合わせ方を定めます。表現方法や実行時検査の有無は、言語仕様と実装を分けて確認します。

\paragraph{型安全性の範囲}
        型が付けば業務上正しいとは限りません。例えば、同じ整数型でも円と個数の取り違えは防げません。

\par
\endgroup
\medskip
\begingroup
\paragraph{静的型付け}
        実行前の解析で式の型整合性を主に検査します。検査を通った後も、配列境界や0除算など別種の実行時エラーは残ります。

\paragraph{動的型付け}
        実行時の値が型を持ち、操作時に適用可能性を検査します。型が存在しないという意味ではありません。

\par
\endgroup
\par
\endgroup


\section{Goの基本型}
\label{sec:03-runtime-data-08}

型という考えを、AIアプリの一実装で使うGoへ具体化します。真偽、整数、浮動小数点、文字列は、それぞれ異なる値と操作を持ちます。入力文を文字列として受け、注文番号を数へ変える境界では、その違いが正しさを左右します。

\begingroup
\begingroup
\paragraph{代表的な基本型}
        Goの基本型は、用途と代表的な例を次のように整理できます。
        \begin{tabularx}{\linewidth}{@{}lY@{}}
          \toprule
          型 & 役割・注意点\\
          \midrule
          \code{bool} & 真偽値\\
          \code{int8}--\code{int64} & 幅を指定した符号付き整数\\
          \code{int}, \code{uint} & 実装依存の幅（32または64ビット）\\
          \code{float32}, \code{float64} & IEEE 754形式の浮動小数点数\\
          \code{complex64}, \code{complex128} & 複素数\\
          \code{string} & 不変なバイト列\\
          \bottomrule
        \end{tabularx}

\par
\endgroup
\medskip
\begingroup
\paragraph{別名}
        \code{byte}は\code{uint8}、\code{rune}は\code{int32}の別名です。runeはUnicodeコードポイントを表す用途に使います。

\paragraph{ゼロ値}
        明示的に初期化していない変数にも、型ごとのゼロ値があります。数値は0、真偽値は\code{false}、文字列は空文字列です。

\par
\endgroup
  \source{The Go Programming Language Specification, “Types”}
\par
\endgroup


\section{サイズとアラインメント}
\label{sec:03-runtime-data-09}

型が決まると値の意味は定まりますが、実際に何バイトをどこへ置くかは実装の都合も受けます。CPUが効率よく読める境界へ値をそろえるため、構造体には見えない隙間が入ることがあります。高位の型が物理メモリへ接する場所です。

\section{Goの値渡し}
\label{sec:03-runtime-data-10}

値の配置が見えたところで、関数から関数へ渡すと何が移動するかを考えます。Goは引数を値としてコピーしますが、その値が別領域への記述子なら、参照先は共有されます。「コピーした」と「独立した」は同じ意味ではありません。

\begingroup
\begingroup
\paragraph{代入と引数渡し}
        代入や関数呼び出しでは値をコピーします。整数や配列を渡すと、その値のコピーを更新しても元の値は変わりません。

\paragraph{ポインタ}
        ポインタ値もコピーされます。コピーされた二つのポインタが同じ対象を指せば、その対象への更新は共有されます。

\par
\endgroup
\medskip
\begingroup
      \centering
      \begin{tikzpicture}[node distance=5mm,every node/.append style={font=\scriptsize}]
        \node[box] (s1) {slice変数 s\\先頭・長さ・容量};
        \node[box,below=of s1] (s2) {コピー t\\先頭・長さ・容量};
        \node[accentbox,right=12mm of $(s1)!0.5!(s2)$] (arr) {共有する\\元配列};
        \draw[flow] (s1) -- (arr);
        \draw[flow] (s2) -- (arr);
      \end{tikzpicture}
      \vspace{3mm}
\paragraph{記述子を持つ値}
        スライス、マップなどをコピーしても、内部のデータ構造を共有する場合があります。共有の単位を確認します。

\par
\endgroup
\par
\endgroup


\section{計算量}
\label{sec:03-runtime-data-11}

要求一件を正しく処理できても、会話履歴や注文明細が増えたとき同じ時間で終わるとは限りません。入力の大きさに応じて操作回数がどう増えるかを表すと、特定の端末で測った一回の速さを越えて、処理の伸び方を比較できます。

\begingroup
\begingroup
      \centering
      \begin{tikzpicture}[x=5mm,y=4mm,every node/.append style={font=\scriptsize}]
        \draw[->,draw=PaleGray] (0,0)--(8.5,0) node[right] {$n$};
        \draw[->,draw=PaleGray] (0,0)--(0,7) node[above] {操作回数};
        \draw[draw=DeepNavy,line width=.7pt] plot[smooth] coordinates {(0,1)(2,1)(4,1)(6,1)(8,1)};
        \node[right] at (8,1) {$O(1)$};
        \draw[draw=MutedBlue,line width=.7pt] plot[smooth] coordinates {(0,0)(2,1.4)(4,2.8)(6,4.2)(8,5.6)};
        \node[right] at (8,5.6) {$O(n)$};
        \draw[draw=PaleGray,line width=.7pt] plot[smooth] coordinates {(0,0)(2,.35)(4,1.4)(6,3.15)(8,5.6)};
        \node[above left] at (7.7,5.3) {$O(n^2)$};
      \end{tikzpicture}
\par
\endgroup
\medskip
\begingroup
\paragraph{入力サイズ $n$}
        要素数、頂点数、桁数など、処理対象の規模を表す量です。何を$n$とするかを先に定義します。

\paragraph{O記法}
        十分大きな$n$で、増え方の上限を定数倍まで無視して表します。実測時間そのものではありません。

\par
\endgroup
  \vspace{3mm}
  \takeaway{同じ$O(n)$でも定数、メモリアクセス、入力分布、実装によって実時間は異なります。}
\par
\endgroup


\section{計算量の評価軸}
\label{sec:03-runtime-data-12}

「速いアルゴリズム」という一語だけでは、実行中の要求を説明しきれません。最悪時か平均時か、時間かメモリか、入力のどの量を増やすかで評価は変わります。前提を明らかにして初めて、計算量は設計判断へ使えます。

\begingroup
\begingroup
\paragraph{時間計算量}
        比較、代入、メモリアクセスなど、計算モデルで定めた基本操作の回数を数えます。

\paragraph{空間計算量}
        入力以外に必要な補助記憶や、再帰スタックを含む使用量の増え方を評価します。

\par
\endgroup
\medskip
\begingroup
\paragraph{線形探索の例}
        配列、連結リスト、ハッシュ表では、探索と更新に必要な計算量が異なります。
        \begin{tabularx}{\linewidth}{@{}lY@{}}
          \toprule
          条件 & 比較回数\\
          \midrule
          最良 & 先頭で一致：$1$\\
          平均 & 分布の仮定に依存\\
          最悪 & 末尾または不在：$n$\\
          \bottomrule
        \end{tabularx}

\paragraph{平均計算量の前提}
        どの入力がどの確率で現れるかを示さない「平均」は再現できません。

\par
\endgroup
  \source{MIT 6.006, “Asymptotic Complexity”}
\par
\endgroup


\section{配列}
\label{sec:03-runtime-data-13}

ここから、複数の値をどんな形で並べるかへ進みます。要素を同じ大きさで連続配置する配列は、番号から位置を直接求められます。注文の明細を順番に処理するような場面で、単純な配置が速いアクセスを生みます。

\begingroup
\begingroup
      \centering
      \begin{tikzpicture}[x=9mm,y=9mm,every node/.append style={font=\scriptsize}]
        \foreach \x/\v in {0/18,1/7,2/31,3/4,4/12,5/9}{
          \draw[draw=RuleGray,fill=CardWhite] (\x,0) rectangle ++(1,1);
          \node at (\x+.5,.5) {\v};
          \node[below,font=\tiny] at (\x+.5,0) {[\x]};
        }
        \draw[flow] (2.5,-1.4)--(2.5,-.1);
        \node[below,font=\scriptsize] at (2.5,-1.5) {base $+ 2\times$要素幅};
      \end{tikzpicture}
      \vspace{4mm}
\paragraph{ランダムアクセス}
        固定幅要素の位置を基準位置と添字から計算できるため、RAMモデルでは読み書きを$O(1)$と扱います。

\par
\endgroup
\medskip
\begingroup
\paragraph{固定長}
        Goの配列型\code{[N]T}では長さ$N$が型の一部です。要素は順に配置されます。

\paragraph{挿入と削除}
        途中へ挿入するには後続要素をずらすため、最悪$O(n)$です。順序を保たないなら別の設計も選べます。

\par
\endgroup
\par
\endgroup


\section{スライス}
\label{sec:03-runtime-data-14}

固定長の配列だけでは、入力ごとに長さが変わる会話や明細を扱いにくくなります。Goのスライスは、配列の一部を長さと容量とともに指し示します。便利な可変長の見た目の下には、共有される配列が残っています。

\begingroup
\begingroup
      \centering

\paragraph{区間の共有}
        \code{s[1:4]}のような再スライスは、通常同じ元配列を参照します。一方の要素更新を別のスライスから観測できます。

\section{appendの動作}
\label{sec:03-runtime-data-15}

スライスへ要素を足すと、空きがある間は同じ配列を使えます。容量を越えた瞬間には、より大きな配列を確保して内容を移します。短い一行の背後で置き場所が変わるため、性能と共有状態の両方に転換点が生まれます。

\begingroup
\begingroup
\paragraph{容量が足りる場合}
        元配列の空き領域へ要素を書き、同じ元配列を参照する可能性があります。別名のスライスにも影響し得ます。

\paragraph{容量が足りない場合}
        より大きな元配列を確保して要素をコピーし、そこを指す新しいスライスを返します。元配列との共有は切れます。

\par
\endgroup
\medskip
\begingroup
\paragraph{appendの返り値}
        \code{s = append(s, x)}のように書きます。再確保の有無と容量の増やし方は、コードから固定値として仮定しません。

\paragraph{償却$O(1)$}
        容量を幾何級数的に増やす動的配列では、複数回の末尾追加へ再確保コストを配ると1回当たり$O(1)$になります。これは一回ごとの最悪時間ではありません。

\par
\endgroup
  \source{Go specification, built-in \code{append}; MIT 6.006, “Dynamic Arrays”}
\par
\endgroup


\section{マップ}
\label{sec:03-runtime-data-16}

配列とスライスは順序に沿う処理へ向きますが、注文番号から対応する注文を探すたびに先頭から歩くのは非効率です。キーから候補位置を計算するマップを使うと、名前や識別子による検索を直接表せます。

\begingroup
\begingroup
      \centering
      \begin{tikzpicture}[node distance=3mm,every node/.append style={font=\scriptsize}]
        \node[box] (key) {キー ``cat''};
        \node[accentbox,right=of key] (hash) {ハッシュ関数};
        \node[box,right=of hash] (idx) {候補 2};
        \draw[flow] (key)--(hash); \draw[flow] (hash)--(idx);
        \node[box,below=8mm of hash,minimum width=46mm] (slots) {0：\quad 1：\quad 2：cat／値\quad 3：dog／値};
        \draw[flow] (idx)--(slots);
      \end{tikzpicture}
      \vspace{2mm}
\paragraph{衝突}
        異なるキーが同じ候補へ対応することがあります。実装はキー比較と追加の探索で区別します。

\par
\endgroup
\medskip
\begingroup
\paragraph{負荷率とリサイズ}
        衝突や探索が増え過ぎないよう、要素数に応じて格納領域を拡張し、配置を組み直す実装があります。

\paragraph{計算量と保証範囲}
        良い分散と適切な負荷率を仮定すれば検索・追加は平均$O(1)$、偏れば最悪$O(n)$です。
        Go仕様は具体的な表構造や反復順を保証しません。

\par
\endgroup
  \source{CMU 15-121, “Hash Tables”; The Go Programming Language Specification}
\par
\endgroup


\section{データ構造の選択}
\label{sec:03-runtime-data-17}

配列、スライス、マップのどれかが常に優れているわけではありません。要求の中で頻繁に行う操作、順序の必要性、更新方法、共有範囲を先に見て、その仕事に合う形を選びます。データの置き方は、その後の処理の流れを決めます。

\begingroup
  \noindent
  \begin{tabularx}{\textwidth}{@{}lYYYY@{}}
    \toprule
    構造 & 添字／キー検索 & 末尾追加 & 途中挿入 & 主な注意点\\
    \midrule
    固定長配列 & $O(1)$ & 対象外 & $O(n)$ & 長さが型に含まれる\\
    動的配列／スライス & $O(1)$ & 償却$O(1)$ & $O(n)$ & 再確保と元配列共有\\
    ハッシュマップ & 平均$O(1)$ & 平均$O(1)$ & 対象外 & 衝突・順序なし\\
    連結リスト & $O(n)$ & 位置次第 & 位置取得後$O(1)$ & ポインタ追跡\\
    \bottomrule
  \end{tabularx}
  \vspace{2mm}
\begingroup
\paragraph{要件から選ぶ}
        順序、重複、検索キー、更新頻度、走査方法、メモリ量を列挙し、頻繁な操作を安くします。

\par
\endgroup
\medskip
\begingroup
\paragraph{記号の前提}
        表は典型的な実装とRAMモデルの値です。平均計算量には入力とハッシュ分布の仮定があります。

\endgroup

\section{Pythonのオブジェクト}
\label{sec:03-runtime-data-18}

ここまでGoで見た原理を別の言語へ移すと、仕様と実装を区別しやすくなります。Pythonでは名前がオブジェクトへ束縛され、代入後も同じ可変オブジェクトを共有することがあります。表面の構文が違っても、値、参照、寿命という問いは残ります。

\begingroup
\begingroup
      \centering
      \begin{tikzpicture}[node distance=6mm,every node/.append style={font=\scriptsize}]
        \node[box] (x) {名前 x};
        \node[box,below=of x] (y) {名前 y};
        \node[accentbox,right=13mm of $(x)!0.5!(y)$] (obj) {オブジェクト\\型：list\\値：[1, 2]};
        \draw[flow] (x)--(obj); \draw[flow] (y)--(obj);
      \end{tikzpicture}
      \vspace{4mm}
\paragraph{共有と可変性}
        \code{y = x}は同じオブジェクトへの束縛を作ります。リストを\code{y.append(3)}で変更すると、\code{x}からも変更後の値が見えます。

\par
\endgroup
\medskip
\begingroup
\paragraph{オブジェクトモデル}
        Pythonのすべてのデータはオブジェクトで、各オブジェクトは同一性、型、値を持ちます。オブジェクトの型は生成後に変わりません。

\paragraph{Goとの比較}
        Pythonは操作時の型検査や属性検索などを実行時に行います。メモリ量と速度差は、言語名だけでなく処理系、値、処理内容を固定して測ります。

\par
\endgroup
  \source{Python 3 Language Reference, “Data model”}
\par
\endgroup


\section{手を動かす：置き方と速さ}
\label{sec:03-runtime-data-19}

理論上の伸び方と、実行環境で観測する速さは互いを補います。スライスとマップの読み出しを同じ条件で測り、値の置き方がCPU時間と割り当てへどう現れるかを確かめます。

\begingroup
\begingroup
      \begin{lstlisting}[language=Go]
var sink int

func BenchmarkSliceIndex(b *testing.B) {
    xs := make([]int, 1<<16)
    b.ResetTimer()
    for i := 0; i < b.N; i++ {
        sink = xs[i&(len(xs)-1)]
    }
}

func BenchmarkMapLookup(b *testing.B) {
    m := make(map[int]int, 1<<16)
    for i := 0; i < 1<<16; i++ { m[i] = i }
    b.ResetTimer()
    for i := 0; i < b.N; i++ {
        sink = m[i&((1<<16)-1)]
    }
}
      \end{lstlisting}
\par
\endgroup
\medskip
\begingroup
\paragraph{実行と比較条件}
        \code{go test -bench=. -benchmem}を5回実行し、\code{ns/op}と\code{allocs/op}を記録します。
        要素数、キー分布、事前確保、CPU、Go版を揃えます。

\paragraph{追加課題}
        \code{append}の初期容量を0と要素数に変え、割り当て回数を比べます。測定値は計算量の証明ではありません。

\section{一要求からシステムへ}
\label{sec:03-runtime-data-20}

保存されていたプログラムは、OSから隔離されたアドレス空間とCPU時間を受け取り、動くプロセスになりました。入力文と注文データは型のある値としてメモリへ置かれ、配列、スライス、マップが処理に合う形で関係を持たせます。ポインタと参照は共有を可能にし、計算量は入力が増えた先の振る舞いを予測させます。

一件の要求がどこで動くかは見えました。しかし実際のAIアプリには、多数の機能と変更が積み重なります。次章では実行中の値から一歩引き、注文の事実、通信の形式、モデルの呼び出しをどう分ければ、システム全体を育て続けられるかを見ます。

\takeaway{プログラムが動くとは、命令だけでなく、OSが与える時間と場所の中で、寿命と共有範囲を持つデータが変化することです。}

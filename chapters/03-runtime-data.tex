\chapter{プログラムが動く場所}
\label{chap:runtime-data}

\begin{chapterabstract}
命令へ変換されたコードは、まだSSDなどの保存装置に置かれたファイルにすぎません。送信ボタンに反応するには、OSからCPUを使う時間とメモリを受け取り、実行中のプログラムであるプロセスにならなければなりません。ここで、プログラムは初めて現実の場所と時間を持ちます。

入力された文は文字列としてメモリへ置かれ、注文番号や会話履歴は型のある値へ組み直されます。値を決まった数だけ順に置くか、増減できる列として扱うか、名前から探せる対応として持つかによって、探し方、共有のされ方、必要な時間と容量が変わります。それぞれを扱う配列、スライス、マップという仕組みは、必要になる節で説明します。この章では、OSが用意する舞台からデータ一つひとつの寿命まで、実行中の要求が占める場所を追います。
\end{chapterabstract}

\begin{learninggoals}
  \item OS、プロセス、システムコール、仮想メモリの責務を区別できます。
  \item 型、値、ポインタ、参照をメモリ上の配置へ結び付けられます。
  \item データ構造を時間計算量と空間計算量から選べます。
\end{learninggoals}

\section{OSの役割}
\label{sec:03-runtime-data-01}

機械語になったAIアプリを起動するとき、CPUや実際に取り付けられたメモリを直接占有することはできません。同じ端末ではブラウザ、エディタ、別のサービスも動いています。CPU時間、メモリ、保存装置など、処理に使える限りあるものをまとめて\term{計算資源}といいます。それらを安全に分け、機器ごとの細かな操作を共通の形で提供するのがOSです。

\begingroup
  \centering
  \begin{tikzpicture}[node distance=3mm,every node/.append style={font=\small}]
    \node[box,minimum width=29mm] (app1) {アプリA};
    \node[box,minimum width=29mm,right=of app1] (app2) {アプリB};
    \node[accentbox,minimum width=68mm,below=of $(app1)!0.5!(app2)$] (os) {OS：抽象化・保護・資源管理};
    \node[box,minimum width=68mm,below=of os] (hw) {CPU・メモリ・ストレージ・入出力装置};
    \draw[flow] (app1) -- (os);
    \draw[flow] (app2) -- (os);
    \draw[flow] (os) -- (hw);
  \end{tikzpicture}
  \vspace{4mm}
\begingroup
\paragraph{抽象化}
        OSは、名前を付けたデータのまとまりであるファイルを提供します。実行中のプログラムであるプロセスも提供します。実際のメモリを扱いやすく見せる仮想メモリも、ハードウェアより扱いやすい単位の一つです。これが第0章で見た抽象化です。

\par
\endgroup
\medskip
\begingroup
\paragraph{保護}
        誰が何を読み書きできるかという許可を\term{権限}といいます。OSは権限と、各プログラムに見せるメモリ範囲を分け、ある処理の誤りが別の処理へ広がる範囲を抑えます。この役割が\term{保護}です。

\par
\endgroup
\medskip
\begingroup
\paragraph{資源管理}
        限りあるCPU時間、物理メモリ、入出力装置を、必要性や優先度に応じて複数の処理へ割り当てます。この調整が\term{資源管理}です。

\par
\endgroup
  \source{Arpaci-Dusseau et al., \textit{Operating Systems: Three Easy Pieces}}
\par
\endgroup


\section{プログラムとプロセス}
\label{sec:03-runtime-data-02}

保存されている命令列はプログラムであり、まだ時間の中を進んでいません。OSが命令とデータをメモリへ配置し、実行位置や資源を管理し始めると、プログラムはプロセスになります。送信イベントを受け取るのはファイルではなく、この動いている存在です。

\begingroup
\begingroup
\paragraph{プログラム}
        \term{プログラム}は、命令や開始時に使うデータを含む、保存された処理の記述です。実行可能ファイルや、別の処理系に読ませる命令文であるスクリプトは、それだけではCPU時間を持ちません。

\paragraph{プロセス}
        \term{プロセス}は、実行中のプログラムに、メモリの見え方、CPUレジスタの現在値、開いているファイルなどを加えたものです。OSが「どこまで実行したか」を保存して再開できるよう、この一式を管理します。

\par
\endgroup
\medskip
\begingroup
\paragraph{スレッド}
        プロセス内で命令を順に実行する一つの流れが\term{スレッド}です。一つのプロセスが複数のスレッドを持つと、同じメモリ上のデータを共有しながら複数の仕事を進められます。各スレッドは、自分が次に実行する位置を含むレジスタ状態と、関数呼び出しを置くスタックを持ちます。

\paragraph{並行性の注意}
        複数の仕事が、開始から終了までの時間を重ねて進む性質を\term{並行性}といいます。共有データへの読み書きが同じ時期に起き、順序によって結果が変わることが\term{競合}です。どの処理を先へ進めてよいかを決める\term{同期}によって、許される順序を定めます。

\par
\endgroup
  \takeaway{同じプログラムを2回起動すると、通常は別のプロセスと別の仮想アドレス空間が作られます。}
\par
\endgroup


\section{システムコール}
\label{sec:03-runtime-data-03}

プロセスは自由に機器を操作できるわけではありません。入力を受け取り、ファイルを読み、ネットワークへ書くときは、保護された境界を越えてOSへ依頼します。アプリからOSの中核へ処理を頼むための決められた入口が\term{システムコール}です。

CPUは、アプリに許す操作を制限した\term{利用者モード}を備えます。OSの中核には、機器やメモリ管理の操作を許す\term{カーネルモード}があります。CPUは二つのモードを区別します。OSの中核部分を\term{カーネル}と呼びます。システムコールは、検査された形で利用者モードからカーネルモードへ移る仕組みです。

\begingroup
\begingroup
      \centering
      \begin{tikzpicture}[node distance=4mm,every node/.append style={font=\small}]
        \node[box,minimum width=58mm] (user) {利用者モード：アプリ／ライブラリ};
        \node[accentbox,minimum width=58mm,below=of user] (gate) {システムコール境界};
        \node[box,minimum width=58mm,below=of gate] (kernel) {カーネル：検査・処理・結果返却};
        \draw[flow] (user) -- node[right,font=\scriptsize]{番号・引数} (gate);
        \draw[flow] (gate) -- (kernel);
        \draw[softflow] (kernel.west) to[bend right=30] node[left,font=\scriptsize]{戻り値} (user.west);
      \end{tikzpicture}
\par
\endgroup
\medskip
\begingroup
\paragraph{代表例}
        ファイルの読み書き、ネットワーク通信、仮想メモリの操作、別プロセスの生成などを依頼します。対象や長さなど、処理へ渡す値を\term{引数}といいます。処理から受け取る成功状態や読み出した量を\term{戻り値}といいます。システムコールでは、何をしてほしいかを示す番号も渡します。

\paragraph{ライブラリとの違い}
        ライブラリの関数には、アプリ内の通常の関数呼び出しだけで完結するものも、内部で複数のシステムコールを使うものもあります。そのため、APIを一回呼ぶことと、システムコールを一回行うことは必ずしも一対一ではありません。

\par
\endgroup
  \source{OSTEP, “Processes” / “Limited Direct Execution”}
\par
\endgroup


\section{仮想メモリ}
\label{sec:03-runtime-data-04}

送信された文を処理するには置き場所が要りますが、すべてのプロセスへ実際のメモリの位置を直接見せると、互いのデータを壊しかねません。コンピュータへ物理的に取り付けられたメモリを\term{物理メモリ}といいます。その上の実際の位置を\term{物理アドレス}といいます。

OSとCPUは、各プロセスに自分専用の連続した空間があるように見せ、必要な物理領域へ対応づけます。この見かけの記憶の仕組みが\term{仮想メモリ}です。プロセスが値の位置として使う番号が\term{仮想アドレス}です。ここで「仮想」は存在しないという意味ではなく、直接の物理位置から一段離した見え方という意味です。

\begingroup
\begingroup
      \centering
      \begin{tikzpicture}[x=0.9mm,y=0.9mm,every node/.append style={font=\scriptsize}]
        \node[box,minimum width=22mm] (va) at (10,22) {仮想アドレス};
        \node[accentbox,minimum width=22mm] (mmu) at (40,22) {MMU};
        \node[box,minimum width=22mm] (pa) at (70,22) {物理アドレス};
        \node[box,minimum width=26mm] (pt) at (40,3) {ページ表};
        \draw[flow] (va) -- (mmu);
        \draw[flow] (mmu) -- (pa);
        \draw[softflow] (pt) -- (mmu);
        \node[font=\scriptsize,align=center] at (40,-9) {未登録・権限違反なら\\ページフォルト};
      \end{tikzpicture}
\par
\endgroup
\medskip
\begingroup
\paragraph{プロセスごとの見え方}
        仮想メモリと物理メモリは、一定の大きさに区切った\term{ページ}単位で対応づけます。どの仮想ページをどの物理ページへ対応させるかを記録した表が\term{ページ表}です。CPU内の\term{MMU}、Memory Management Unitは、この表を使ってアドレスを変換する装置です。そのため、同じ数値の仮想アドレスでも、プロセスごとに異なる物理ページへ対応できます。

\paragraph{得られる性質}
        ページ表に対応がない、または許されない読み書きをしたとき、CPUは\term{ページフォルト}という例外をOSへ知らせます。OSは必要なページを用意できるなら処理を続け、無効なアクセスならプロセスへエラーを返します。

        この仕組みにより、プロセス同士の分離、使う場所だけが物理メモリへ対応する空間、意図的に同じ物理ページを見せる共有、必要になった時点での割り当てを実現できます。

\par
\endgroup
  \vspace{3mm}
  \takeaway{仮想アドレスは物理メモリ上の位置そのものではなく、変換に使う名前です。}
\par
\endgroup


\section{アドレス空間}
\label{sec:03-runtime-data-05}

一つのプロセスから見える仮想アドレスの範囲と、その中の配置をまとめて\term{アドレス空間}といいます。その中でも値の役割と寿命は同じではありません。命令、固定データ、関数呼び出しの途中状態、実行中に増減する値を分けて置くことで、プロセスは大きな処理を整理します。

\begingroup
\begingroup
      \centering
      \begin{tikzpicture}[x=1mm,y=1mm,every node/.append style={font=\scriptsize}]
        \draw[draw=MutedBlue] (0,0) rectangle (35,52);
        \fill[PaleBlue] (0,0) rectangle (35,10);
        \fill[CardWhite] (0,10) rectangle (35,21);
        \fill[PaleBlue] (0,21) rectangle (35,36);
        \fill[CardWhite] (0,36) rectangle (35,52);
        \draw[RuleGray] (0,10)--(35,10) (0,21)--(35,21) (0,36)--(35,36);
        \node at (17.5,5) {コード／静的データ};
        \node at (17.5,15.5) {ヒープ $\uparrow$};
        \node[color=PaleGray] at (17.5,28.5) {未割り当て領域};
        \node at (17.5,44) {$\downarrow$ スタック};
      \end{tikzpicture}
\par
\endgroup
\medskip
\begingroup
\paragraph{スタック}
        \term{スタック領域}は、第2章で見た関数呼び出しのフレームを後入れ先出しで管理する領域です。戻り先や、その呼び出しだけで使う値を置き、関数の終了に合わせてまとめて巻き戻せます。

\paragraph{ヒープ}
        一つの関数呼び出しが終わった後も必要な値や、大きさと寿命を実行中に決める値を置く領域が\term{ヒープ}です。メモリ上に必要な大きさの場所を用意することを\term{確保}といいます。不要になった場所を別の値に使えるよう戻すことを\term{解放}といいます。

        言語が提供する実行時の支援処理を\term{ランタイム}といいます。ヒープの空きを管理して場所を割り当てる仕組みを\term{アロケータ}といいます。ヒープ上の値をいつ解放するかは、言語と処理系によってプログラマまたはランタイムが管理します。

\par
\endgroup

\par
\endgroup


\section{ポインタと参照}
\label{sec:03-runtime-data-06}

値を別の関数へ渡すたびにすべて複製すると、大きな会話履歴や注文情報の扱いは重くなります。そこで、値そのものではなく置き場所を示し、同じ領域を複数の箇所から参照します。効率を得る代わりに、誰と状態を共有しているかを意識する必要が生まれます。

\begingroup
\begingroup
\paragraph{ポインタ／参照}
        別の値が置かれた場所を示す値が\term{ポインタ}です。ある値そのものではなく、その値へ到達する関係を広く\term{参照}と呼びます。言語によって二語の厳密な使い分けは異なります。複数の変数が同じ対象を参照すると、一方を通した更新を他方からも観測できます。

\par
\endgroup
\medskip
\begingroup
\paragraph{寿命の誤り}
        値を利用できる期間が\term{寿命}です。すでに解放した領域を指し続けるポインタを使ったり、まだ必要な値を早く解放したりすると、許されない場所を読む不正アクセスにつながります。

\par
\endgroup
\medskip
\begingroup
\paragraph{GC}
        \term{ガベージコレクション}は、どの変数からも到達できなくなった値など、今後使えない領域をランタイムが見つけて自動で再利用する仕組みです。Garbage Collectionを略して\term{GC}と呼びます。プログラマがメモリを一個ずつ解放する負担を減らしますが、ファイルや通信接続まで特定の時刻に閉じる保証ではありません。

\par
\endgroup
  \vspace{4mm}
\paragraph{Goでの境界}
    Goはポインタを持ちますが、ポインタへ数を足して別の位置を直接作る通常のポインタ演算は認めません。関数を終えても参照され得る値を調べる処理を\term{エスケープ解析}といい、値をスタックかヒープのどちらへ置くかは、この解析などを用いる処理系の判断です。

  \source{The Go Programming Language Specification; Go FAQ, “stack or heap”}
\par
\endgroup


\section{型}
\label{sec:03-runtime-data-07}

メモリ上では、注文番号も文字列もポインタもビットの並びです。プログラムがそれらを取り違えずに操作できるのは、値の種類と許される操作を\term{型}として定めるからです。第1章で外側にあった解釈規則が、ここでは言語の約束として現れます。

\begingroup
\begingroup
\paragraph{型が表すもの}
        型は、その型に含まれる値の範囲、利用できる演算、式の組み合わせ方を定めます。たとえば真偽値には真と偽があり、整数には加算ができます。言語が外から約束する規則が\term{言語仕様}です。その約束を実際に動かすコンパイラやランタイムが\term{実装}です。二つは分けて考えます。

\paragraph{型安全性の範囲}
        型の規則に反する操作を防げる性質を\term{型安全性}といいます。ただし、型が付けば業務上正しいとは限りません。例えば、どちらも同じ整数型なら、円と個数の取り違えは防げません。別の型として定義すれば、区別を強くできます。

\par
\endgroup
\medskip
\begingroup
\paragraph{静的型付け}
        プログラムを実行する前に、式や関数の型が規則どおり組み合わさるか主に検査する方式が\term{静的型付け}です。検査を通った後も、配列の範囲外アクセスや0除算など、実際の値によって決まるエラーは残ります。

\paragraph{動的型付け}
        実行中の値が型を持ち、操作しようとした時点でその操作が可能か主に検査する方式が\term{動的型付け}です。型が存在しないという意味ではありません。

\par
\endgroup
\par
\endgroup


\section{Goの基本型}
\label{sec:03-runtime-data-08}

型という考えを、AIアプリの一実装で使うGoへ具体化します。真偽、整数、浮動小数点、文字列は、それぞれ異なる値と操作を持ちます。入力文を文字列として受け、注文番号を数へ変える境界では、その違いが正しさを左右します。

\begingroup
\begingroup
\paragraph{代表的な基本型}
        ほかの型を組み立てる土台として言語が用意する型を\term{基本型}といいます。Goの基本型は、用途と代表的な例を次のように整理できます。\code{bool}は真か偽、\code{int}はintegerすなわち整数、\code{uint}のuはunsignedすなわち符号なしを表します。
        \begin{tabularx}{\linewidth}{@{}lY@{}}
          \toprule
          型 & 役割・注意点\\
          \midrule
          \code{bool} & 真偽値\\
          \code{int8}--\code{int64} & 幅を指定した符号付き整数\\
          \code{int}, \code{uint} & 実装依存の幅（32または64ビット）\\
          \code{float32}, \code{float64} & 標準規格IEEE 754に沿う浮動小数点数\\
          \code{complex64}, \code{complex128} & 実数部と虚数部を組にした複素数\\
          \code{string} & 不変なバイト列\\
          \bottomrule
        \end{tabularx}

\par
\endgroup
\medskip
\begingroup
\paragraph{別名}
        同じ型へ別の名前を付けたものを\term{別名}といいます。\code{byte}は\code{uint8}、\code{rune}は\code{int32}の別名です。runeはUnicodeコードポイントを表す用途に使います。

\paragraph{ゼロ値}
        変数へ最初の値を設定することを\term{初期化}といいます。Goでは明示的に初期化していない変数にも、型ごとに決めた\term{ゼロ値}が入ります。数値は0、真偽値は\code{false}、文字列は長さ0の空文字列です。

\par
\endgroup
  \source{The Go Programming Language Specification, “Types”}
\par
\endgroup


\section{サイズとアラインメント}
\label{sec:03-runtime-data-09}

型が決まると値の意味は定まりますが、実際に何バイトをどこへ置くかは実装の都合も受けます。CPUが効率よく読める位置へ値の先頭をそろえる規則を\term{アラインメント}といいます。この規則に合わせるため、構造体には値を置かない隙間が入ることがあります。高位の型が物理メモリへ接する場所です。

\begingroup
\begingroup
      \centering
      \begin{tikzpicture}[x=8mm,y=8mm,every node/.append style={font=\scriptsize}]
        \foreach \x in {0,...,7}{\draw[draw=RuleGray,fill=CardWhite] (\x,0) rectangle ++(1,1);}
        \fill[PaleBlue] (0,0) rectangle ++(1,1);
        \fill[MutedBlue!25] (4,0) rectangle ++(4,1);
        \node at (0.5,0.5) {A};
        \node[color=PaleGray] at (2.5,0.5) {padding};
        \node at (5.5,0.5) {B};
        \foreach \x in {0,...,7}{\node[below,font=\tiny] at (\x+0.5,0) {\x};}
      \end{tikzpicture}
      \vspace{2mm}
\paragraph{なぜ隙間が生じるか}
        4バイトの値を4の倍数のアドレスから置く、といった区切りが\term{アラインメント境界}です。値の開始位置をこの境界へ合わせるため、構造体のフィールド間や末尾に未使用のバイトが入る場合があります。この隙間を\term{パディング}といいます。

\par
\endgroup
\medskip
\begingroup
\paragraph{確認方法}
        Goでは\code{unsafe.Sizeof}で、対象の実行ファイルを作る条件における大きさを調べられます。\code{unsafe.Alignof}は境界を調べます。\code{unsafe.Offsetof}は先頭からの位置を調べます。\code{unsafe}という名前は、型が通常守る一部の安全性をプログラマの責任で越える機能であることを示します。

\paragraph{仕様との区別}
        ポインタや\code{int}のサイズ、構造体の総サイズは、CPUとOSの組合せや言語処理系に依存します。図の配置は一例です。

\par
\endgroup
  \source{The Go Programming Language Specification, “Size and alignment guarantees”}
\par
\endgroup


\section{Goの値渡し}
\label{sec:03-runtime-data-10}

値の配置が見えたところで、関数から関数へ渡すと何が移動するかを考えます。Goは引数として受け取った値を複製します。この方式を\term{値渡し}といいます。ただし、その値が別領域を指し示す小さな情報のまとまりなら、指し示した先は共有されます。「値をコピーした」と「指し示した先まで独立した」は同じ意味ではありません。

\begingroup
\begingroup
\paragraph{代入と引数渡し}
        変数へ値を入れる\term{代入}や関数呼び出しでは、値をコピーします。整数や配列を渡すと、その値のコピーを更新しても元の値は変わりません。

\paragraph{ポインタ}
        ポインタ値もコピーされます。コピーされた二つのポインタが同じ対象を指せば、その対象への更新は共有されます。

\par
\endgroup
\medskip
\begingroup
      \centering
      \begin{tikzpicture}[node distance=5mm,every node/.append style={font=\scriptsize}]
        \node[box] (s1) {slice変数 s\\先頭・長さ・容量};
        \node[box,below=of s1] (s2) {コピー t\\先頭・長さ・容量};
        \node[accentbox,right=12mm of $(s1)!0.5!(s2)$] (arr) {共有する\\元配列};
        \draw[flow] (s1) -- (arr);
        \draw[flow] (s2) -- (arr);
      \end{tikzpicture}
      \vspace{3mm}
\paragraph{記述子を持つ値}
        別のデータがある場所や長さなどをまとめた小さな値を\term{記述子}と呼びます。スライスやマップの記述子をコピーしても、内部のデータ構造を共有する場合があります。何が複製され、何が共有されるかを型ごとに確認します。

\par
\endgroup
\par
\endgroup


\section{計算量}
\label{sec:03-runtime-data-11}

要求一件を正しく処理できても、会話履歴や注文明細が増えたとき同じ時間で終わるとは限りません。入力の大きさに応じて、必要な時間や記憶量がどう増えるかを表したものが\term{計算量}です。特定の端末で測った一回の秒数ではなく、入力が増えたときの伸び方を比較できます。

\begingroup
\begingroup
      \centering
      \begin{tikzpicture}[x=5mm,y=4mm,every node/.append style={font=\scriptsize}]
        \draw[->,draw=PaleGray] (0,0)--(8.5,0) node[right] {$n$};
        \draw[->,draw=PaleGray] (0,0)--(0,7) node[above] {操作回数};
        \draw[draw=DeepNavy,line width=.7pt] plot[smooth] coordinates {(0,1)(2,1)(4,1)(6,1)(8,1)};
        \node[right] at (8,1) {$O(1)$};
        \draw[draw=MutedBlue,line width=.7pt] plot[smooth] coordinates {(0,0)(2,1.4)(4,2.8)(6,4.2)(8,5.6)};
        \node[right] at (8,5.6) {$O(n)$};
        \draw[draw=PaleGray,line width=.7pt] plot[smooth] coordinates {(0,0)(2,.35)(4,1.4)(6,3.15)(8,5.6)};
        \node[above left] at (7.7,5.3) {$O(n^2)$};
      \end{tikzpicture}
\par
\endgroup
\medskip
\begingroup
\paragraph{入力サイズ $n$}
        処理対象の規模を一つの数で表したものが\term{入力サイズ}です。配列なら要素数、グラフなら節点数、数値処理なら桁数などを使います。慣例として$n$と書くことが多いものの、何を$n$とするかを先に定めます。

\paragraph{O記法}
        入力が十分大きくなったときの増え方の上限を簡潔に表す方法が\term{O記法}です。$O(1)$は入力が増えても基本操作の回数が一定の範囲、$O(n)$は入力にほぼ比例、$O(n^2)$は入力を二倍にすると主要部分が約四倍になる増え方です。細かな一定回数や一定倍率を省くため、実測時間そのものではありません。

\par
\endgroup
  \vspace{3mm}
  \takeaway{同じ$O(n)$でも定数、メモリアクセス、入力分布、実装によって実時間は異なります。}
\par
\endgroup


\section{計算量の評価軸}
\label{sec:03-runtime-data-12}

問題を解くために、有限の手順を順序立てて定めたものが\term{アルゴリズム}です。「速いアルゴリズム」という一語だけでは、実行中の要求を説明しきれません。最悪時か平均時か、時間かメモリか、入力のどの量を増やすかで評価は変わります。前提を明らかにして初めて、計算量は設計判断へ使えます。

\begingroup
\begingroup
\paragraph{時間計算量}
        入力サイズに応じた基本操作の回数の増え方が\term{時間計算量}です。比較、代入、メモリアクセスなど、何を一回と数えるかは分析用の単純化した機械である\term{計算モデル}で定めます。

\paragraph{空間計算量}
        入力サイズに応じた使用メモリの増え方が\term{空間計算量}です。入力そのもの以外に必要な一時領域や、再帰のスタックも含めるかを明示します。

\par
\endgroup
\medskip
\begingroup
\paragraph{線形探索の例}
        先頭から一つずつ順番に比較する方法が\term{線形探索}です。最初で見つかる場合、最後で見つかる場合、存在しない場合で比較回数が変わります。
        \begin{tabularx}{\linewidth}{@{}lY@{}}
          \toprule
          条件 & 比較回数\\
          \midrule
          最良 & 先頭で一致：$1$\\
          平均 & 分布の仮定に依存\\
          最悪 & 末尾または不在：$n$\\
          \bottomrule
        \end{tabularx}

\paragraph{平均計算量の前提}
        最も少ない操作で終わる場合を\term{最良計算量}といいます。最も多く必要な場合を\term{最悪計算量}といいます。入力ごとの起こりやすさを加味した平均を\term{平均計算量}といいます。どの入力がどの確率で現れるかを示さない「平均」は再現できません。

\par
\endgroup
  \source{MIT 6.006, “Asymptotic Complexity”}
\par
\endgroup


\section{配列}
\label{sec:03-runtime-data-13}

ここから、複数の値をどんな形で並べるかへ進みます。値を保存し、探し、追加するための形と操作をまとめて\term{データ構造}といいます。同じ型の値を、決めた個数だけメモリ上へ順番に並べたデータ構造が\term{配列}です。一個一個の値を\term{要素}といいます。先頭を0として各要素へ付けた番号を\term{添字}といいます。

\begingroup
\begingroup
      \centering
      \begin{tikzpicture}[x=9mm,y=9mm,every node/.append style={font=\scriptsize}]
        \foreach \x/\v in {0/18,1/7,2/31,3/4,4/12,5/9}{
          \draw[draw=RuleGray,fill=CardWhite] (\x,0) rectangle ++(1,1);
          \node at (\x+.5,.5) {\v};
          \node[below,font=\tiny] at (\x+.5,0) {[\x]};
        }
        \draw[flow] (2.5,-1.4)--(2.5,-.1);
        \node[below,font=\scriptsize] at (2.5,-1.5) {base $+ 2\times$要素幅};
      \end{tikzpicture}
      \vspace{4mm}
\paragraph{ランダムアクセス}
        配列の先頭位置を\term{基準位置}とすると、要素の位置は「基準位置＋添字$\times$一要素のバイト数」で求められます。途中を順番に読まず、指定した位置へ直接アクセスできる性質が\term{ランダムアクセス}です。ここでrandomは「無作為」ではなく「どの位置でも直接」という意味です。各メモリアクセスを一定時間とみなすRAMモデルでは、読み書きを$O(1)$と扱います。

\par
\endgroup
\medskip
\begingroup
\paragraph{固定長}
        作成後に要素数を変えない配列が\term{固定長配列}です。Goの配列型\code{[N]T}では、$N$は要素数、$T$は要素の型を表し、長さ$N$も型の一部です。

\paragraph{挿入と削除}
        途中へ新しい要素を入れる操作が\term{挿入}です。要素を取り除く操作が\term{削除}です。並び順を保ったまま挿入や削除をするには後ろの要素をずらすため、最悪$O(n)$です。

\par
\endgroup
\par
\endgroup


\section{スライス}
\label{sec:03-runtime-data-14}

固定長の配列だけでは、入力ごとに長さが変わる会話や明細を扱いにくくなります。Goの\term{スライス}は、配列の連続した一部分を、現在使う長さと追加できる範囲とともに指し示す値です。要素を増減できる見た目の下には、実際に要素を置く配列が残っています。

\begingroup
\begingroup
      \centering
      \begin{tikzpicture}[x=9mm,y=8mm,every node/.append style={font=\scriptsize}]
        \draw[draw=MutedBlue,fill=PaleBlue] (0,3) rectangle (3,4);
        \draw[RuleGray] (1,3)--(1,4) (2,3)--(2,4);
        \node at (.5,3.5) {ptr}; \node at (1.5,3.5) {len}; \node at (2.5,3.5) {cap};
        \foreach \x/\v in {0/a,1/b,2/c,3/d,4/e,5/f}{
          \draw[draw=RuleGray,fill=CardWhite] (\x,0) rectangle ++(1,1);
          \node at (\x+.5,.5) {\v};
        }
        \draw[flow] (.5,3)--(1.5,1);
        \draw[draw=MutedBlue,line width=.7pt] (1,1.25)--(4,1.25);
        \node[above] at (2.5,1.25) {len = 3};
        \draw[draw=PaleGray,line width=.7pt] (1,-.35)--(6,-.35);
        \node[below] at (3.5,-.35) {cap = 5};
      \end{tikzpicture}
\par
\endgroup
\medskip
\begingroup
\paragraph{三つの情報}
        スライスで、現在見えている要素数を\term{長さ}といいます。先頭から元配列上で利用できる最大要素数を\term{容量}といいます。スライスは、この二つと先頭要素への参照を持ちます。Goでは長さを\code{len}、容量を\code{cap}で調べます。具体的な内部配置は言語仕様の約束ではありません。

\paragraph{区間の共有}
        すでにあるスライスから別の連続範囲を取り出す操作を\term{再スライス}といいます。\code{s[1:4]}は添字1から3までを指し、通常は元と同じ配列を参照します。一方の要素更新を、同じ範囲を共有する別のスライスから観測できます。

\par
\endgroup
  \source{Go Blog, “Go Slices: usage and internals”; Go specification, “Slice types”}
\par
\endgroup


\section{appendの動作}
\label{sec:03-runtime-data-15}

Goでスライスの末尾へ要素を加える組み込み関数が\code{append}です。空きがある間は同じ配列を使えます。容量を越えた瞬間には、より大きな配列を確保して内容を移します。短い一行の背後で置き場所が変わるため、性能と共有状態の両方に転換点が生まれます。

\begingroup
\begingroup
\paragraph{容量が足りる場合}
        元配列の空き領域へ要素を書き、同じ元配列を参照する可能性があります。別名のスライスにも影響し得ます。

\paragraph{容量が足りない場合}
        より大きな元配列を確保して要素をコピーし、そこを指す新しいスライスを返します。このように置き場所を作り直すことを\term{再確保}といいます。古い元配列との共有は切れます。

\par
\endgroup
\medskip
\begingroup
\paragraph{appendの返り値}
        \code{s = append(s, x)}のように書きます。再確保の有無と容量の増やし方は、コードから固定値として仮定しません。

\paragraph{償却$O(1)$}
        長さを実行中に増減できる配列を\term{動的配列}といいます。容量を一定の倍率で増やす動的配列では、ときどき起きる大きなコピーの費用を多数回の末尾追加へ均すと、一回当たり$O(1)$になります。この考え方が\term{償却計算量}です。すべての一回が必ず一定時間という意味ではありません。

\par
\endgroup
  \source{Go specification, built-in \code{append}; MIT 6.006, “Dynamic Arrays”}
\par
\endgroup


\section{マップ}
\label{sec:03-runtime-data-16}

配列とスライスは順序に沿う処理へ向きますが、注文番号から対応する注文を探すたびに先頭から歩くのは非効率です。検索に使う値を\term{キー}といいます。キーに対応して保存するデータを\term{値}といいます。この組を保存するデータ構造が\term{マップ}です。Goのマップは、キーから格納候補の位置を計算するハッシュ表を使って実装されますが、言語仕様は内部方式を固定していません。

キーを、格納候補を選ぶための一定範囲の数値へ変える処理が\term{ハッシュ関数}です。同じキーには同じ結果を返し、異なるキーが候補全体へ偏り過ぎず分かれることを目指します。

\begingroup
\begingroup
      \centering
      \begin{tikzpicture}[node distance=3mm,every node/.append style={font=\scriptsize}]
        \node[box] (key) {キー ``cat''};
        \node[accentbox,right=of key] (hash) {ハッシュ関数};
        \node[box,right=of hash] (idx) {候補 2};
        \draw[flow] (key)--(hash); \draw[flow] (hash)--(idx);
        \node[box,below=8mm of hash,minimum width=46mm] (slots) {0：\quad 1：\quad 2：cat／値\quad 3：dog／値};
        \draw[flow] (idx)--(slots);
      \end{tikzpicture}
      \vspace{2mm}
\paragraph{衝突}
        ハッシュ関数の出力範囲は有限なので、異なるキーが同じ候補へ対応することがあります。これを\term{衝突}といいます。実装は元のキーを比較し、別の空き場所を探すか、同じ候補へ複数の組を持つことで区別します。

\par
\endgroup
\medskip
\begingroup
\paragraph{負荷率とリサイズ}
        用意した格納場所の数に対する要素数の割合を\term{負荷率}といいます。負荷率が高いと衝突が増えやすいため、格納領域を大きくし、各キーの配置を計算し直す実装があります。この拡張を\term{リサイズ}といいます。

\paragraph{計算量と保証範囲}
        ハッシュ値が候補へ偏らず分かれることを\term{分散}といいます。良い分散と適切な負荷率を仮定すれば検索・追加は平均$O(1)$ですが、多くのキーが同じ候補へ偏れば最悪$O(n)$です。
        Go仕様は具体的な表構造や反復順を保証しません。

\par
\endgroup
  \source{CMU 15-121, “Hash Tables”; The Go Programming Language Specification}
\par
\endgroup


\section{データ構造の選択}
\label{sec:03-runtime-data-17}

配列、スライス、マップのどれかが常に優れているわけではありません。要求の中で頻繁に行う操作、順序の必要性、更新方法、共有範囲を先に見て、その仕事に合う形を選びます。データの置き方は、その後の処理の流れを決めます。

比較のため、各要素が次の要素への参照を持ち、鎖のようにつながる\term{連結リスト}も表へ加えます。途中の要素が分かっていれば参照をつなぎ替えて挿入できますが、$i$番目へ行くには先頭から参照をたどります。

\begingroup
  \noindent
  \begin{tabularx}{\textwidth}{@{}lYYYY@{}}
    \toprule
    構造 & 添字／キー検索 & 末尾追加 & 途中挿入 & 主な注意点\\
    \midrule
    固定長配列 & $O(1)$ & 対象外 & $O(n)$ & 長さが型に含まれる\\
    動的配列／スライス & $O(1)$ & 償却$O(1)$ & $O(n)$ & 再確保と元配列共有\\
    ハッシュマップ & 平均$O(1)$ & 平均$O(1)$ & 対象外 & 衝突・順序なし\\
    連結リスト & $O(n)$ & 位置次第 & 位置取得後$O(1)$ & ポインタ追跡\\
    \bottomrule
  \end{tabularx}
  \vspace{2mm}
\begingroup
\paragraph{要件から選ぶ}
        システムに必要な条件を\term{要件}といいます。順序を保つか、同じ値を重複して持てるか、何を検索キーにするか、どれだけ更新するか、どの順に走査するか、使えるメモリ量はいくつかを明らかにし、頻繁な操作の計算量を小さくします。

\par
\endgroup
\medskip
\begingroup
\paragraph{記号の前提}
        表は典型的な実装とRAMモデルの値です。平均計算量には入力とハッシュ分布の仮定があります。

\par
\endgroup
\par
\endgroup


\section{Pythonのオブジェクト}
\label{sec:03-runtime-data-18}

ここまでGoで見た原理を別の言語へ移すと、仕様と実装を区別しやすくなります。Pythonでは、型と値を持ちプログラムから操作される一個の対象を\term{オブジェクト}といいます。名前はオブジェクトと結び付けられます。この結び付きを\term{束縛}と呼びます。代入後も同じオブジェクトを共有することがあるため、表面の構文が違っても、値、参照、寿命という問いは残ります。

\begingroup
\begingroup
      \centering
      \begin{tikzpicture}[node distance=6mm,every node/.append style={font=\scriptsize}]
        \node[box] (x) {名前 x};
        \node[box,below=of x] (y) {名前 y};
        \node[accentbox,right=13mm of $(x)!0.5!(y)$] (obj) {オブジェクト\\型：list\\値：[1, 2]};
        \draw[flow] (x)--(obj); \draw[flow] (y)--(obj);
      \end{tikzpicture}
      \vspace{4mm}
\paragraph{共有と可変性}
        作成後に内部の値を変更できる性質を\term{可変}といいます。作成後に変更できない性質を\term{不変}といいます。\code{y = x}は同じオブジェクトへの束縛を作ります。可変な並びであるリストを\code{y.append(3)}で変更すると、\code{x}からも変更後の値が見えます。

\par
\endgroup
\medskip
\begingroup
\paragraph{オブジェクトモデル}
        オブジェクトがどの性質を持ち、名前や演算とどう関わるかを定めた規則が\term{オブジェクトモデル}です。Pythonの各オブジェクトは、別のオブジェクトと区別する同一性、型、値を持ちます。オブジェクトの型は生成後に変わりません。

\paragraph{Goとの比較}
        Pythonは操作時の型検査や、オブジェクトが持つ名前付きの値や処理を探す属性検索などを実行時に行います。メモリ量と速度差は、言語名だけから決めず、処理系、値、処理内容をそろえて測ります。

\par
\endgroup
  \source{Python 3 Language Reference, “Data model”}
\par
\endgroup


\section{手を動かす：置き方と速さ}
\label{sec:03-runtime-data-19}

理論上の伸び方と、実行環境で観測する速さは互いを補います。同じ処理を何度も実行して時間やメモリ量を測る試験を\term{ベンチマーク}といいます。スライスとマップの読み出しを同じ条件で測り、値の置き方がCPU時間とメモリ確保へどう現れるかを確かめます。

\begingroup
\begingroup
      \begin{lstlisting}[language=Go]
var sink int

func BenchmarkSliceIndex(b *testing.B) {
    xs := make([]int, 1<<16)
    b.ResetTimer()
    for i := 0; i < b.N; i++ {
        sink = xs[i&(len(xs)-1)]
    }
}

func BenchmarkMapLookup(b *testing.B) {
    m := make(map[int]int, 1<<16)
    for i := 0; i < 1<<16; i++ { m[i] = i }
    b.ResetTimer()
    for i := 0; i < b.N; i++ {
        sink = m[i&((1<<16)-1)]
    }
}
      \end{lstlisting}
\par
\endgroup
\medskip
\begingroup
\paragraph{実行と比較条件}
        \code{go test -bench=. -benchmem}を5回実行します。\code{ns/op}は一操作当たりのナノ秒、\code{allocs/op}は一操作当たりのメモリ確保回数です。ナノ秒は十億分の一秒です。
        要素数、キー分布、事前確保、CPU、Go版を揃えます。

\paragraph{追加課題}
        \code{append}の初期容量を0と要素数に変え、割り当て回数を比べます。測定値は計算量の証明ではありません。

\par
\endgroup
\par

\section{一要求からシステムへ}
\label{sec:03-runtime-data-20}

保存されていたプログラムは、OSから隔離されたアドレス空間とCPU時間を受け取り、動くプロセスになりました。入力文と注文データは型のある値としてメモリへ置かれ、配列、スライス、マップが処理に合う形で関係を持たせます。ポインタと参照は共有を可能にし、計算量は入力が増えた先の振る舞いを予測させます。

一件の要求がどこで動くかは見えました。しかし実際のAIアプリには、多数の機能と変更が積み重なります。次章では実行中の値から一歩引き、注文の事実、通信の形式、モデルの呼び出しをどう分ければ、システム全体を育て続けられるかを見ます。

\takeaway{プログラムが動くとは、命令だけでなく、OSが与える時間と場所の中で、寿命と共有範囲を持つデータが変化することです。}
